## 目的と利用環境

- 滅多に取り出さない個人データの長期保存・管理を容易にする。保存コストを重視する。
- 個人運用であり、クラウドインフラの課金額を抑えることを最優先の設計判断とする。通常の参照のために管理対象件数に比例するAPI呼び出しを発生させない。
- 実行者は本人のみ。現在の実行環境は1台の x86_64 macOS PC。
- 将来的な ARM macOS / ARM Linux への移行を考慮する。設定・インデックス等の必要なファイルを移し、対象環境向けにCLIを再ビルドすれば利用を継続できること。
- pure Rust自体を必須条件にはしない。目的は追加の実行時依存をなくすことであり、C等を使ってもその条件を満たす方式なら許容する。
- 追加インストールが必要なC共有ライブラリ等に実行時依存しない。OS標準の共有ライブラリ・ランタイムへのリンクは許容する。
- 同一PC内で複数CLIプロセスの同時実行を想定する。コマンド単位の排他や操作状態の明示的な管理は要求しない。
- 初期保存容量は約2 TB、増加量は年間数百GB、想定する単一ファイルの最大サイズは約100 GB。
- 実データの件数・サイズ分布・取り出し単位は未計測。件数の受入は本書の1万/10万/100万件の条件で行い、未計測を理由に今回の判断待ちにしない。

### 移植性の範囲

- 設定とインデックスの保存形式は、元のOS・CPUアーキテクチャでしか読めないものにしない。CLIの再ビルド後も既存ファイルを利用できること。
- 別途インストールするDB・TLSライブラリ・外部コマンド等を、CLIが実行時に必要とする構成にしない。
- AWS認証・接続設定は外部で用意する。アプリ固有の設定・インデックスの可搬性と、移行先のAWS認証設定は分けて扱う。
- 静的リンクを含む具体的な実現方式と、ビルド時のツールチェーン構成は設計段階で検討する。
- macOSの通常のRust標準ライブラリが使う `libSystem` 等、OS標準の共有ライブラリへのリンクは許容する。追加の外部ライブラリを実行時に導入する必要がないことを求める。

根拠: [Rust標準ライブラリのApple向けリンク設定](https://doc.rust-lang.org/src/std/sys/pal/unix/mod.rs.html)、[Rustの静的・動的Cランタイム](https://doc.rust-lang.org/reference/linkage.html)。

## インターフェースと拡張性

- 構成をなるべくシンプルにし、処理を動かすときは利用者が明示的に実行することを基本とする（2026-11-21、質問29の判断理由）。ローカル表示の問い合わせ・明示再読込・リモート情報の再照合を区別し、自動監視・定期更新・実行をまたぐ回復/再送の管理を追加しない。
- Phase 1で大容量転送に対応するCLIを先に提供し、一覧専用GUIは最後のPhase 3で提供する。
- コア機能を `sync`・`index` クレートとして CLI から分離する。
- インデックスの実現技術も差し替え可能にする。保存・検索・更新の契約を抽象化し、SQLite・redb等の型・クエリ・テーブル操作・保存形式の詳細はinfra層のadapterへカプセル化する。
- CLI・sync・インデックスの業務ロジックは具象DBへ依存しない。別のDB adapterへ置き換えるためにコアの業務判断を変更する構成にしない。
- 具象DBのエラー原因は詳細情報として保持できる一方、コアの公開APIを具象DBのエラー型に固定しない。
- adapterの差し替えと、既存DBファイルの別形式への変換は分けて扱う。別DB形式・将来の未対応スキーマへの自動変換は今回の完成範囲に含めない（2026-11-20確定）。
- Slintの独立アプリとして一覧専用GUIを提供し、Finderのカラム表示に倣った横並びの列で階層構造を表示する。CLIと同じ設定・インデックスを利用し、コアを再利用する。GUIの要件は [GUI要件](gui/REQUIREMENTS.md) にも記載する。
- 初期のリモートストアは AWS S3。将来 Backblaze B2 等を追加できるよう port / adapter で分離する。
- 読み取り側（load）と書き込み側（save）の責務を分離し、コアの契約を S3 固有の仕様に依存させない。
- 実装が対応する URI を任意に指定して操作できること。操作対象の事前登録を必須にしない。
- 引数なしの `ls` は、インデックスに存在するストアのルートを返す。例: `s3://bucket-a`、`b2://bucket-b`。
- インデックスの管理単位はオブジェクトとする。バケットだけを独立した管理対象として登録・保持しない。ルート一覧は記録済みオブジェクトから導出し、最後のオブジェクト記録がなくなったバケットはルート一覧・GUIのバケット一覧から自動的に消える。

### 共通用語（ユビキタス言語）

2026-11-21に確定。以下の用語を要件・設計・画面・ログで共通して使う。

| 呼び名 | 意味 | S3アクセス | 操作の対応 |
| --- | --- | --- | --- |
| 再読込 / Reload | ローカルの設定・インデックスを読み直し、画面の表示済み情報へ反映する | なし。S3インデックス自身のHEAD/GETも行わない | GUIの独立した再読込操作。CLIは通常の参照時にローカルを読む |
| 再照合 / Reconcile | 指定URI・範囲の実ストア状態をその実行で取得し、インデックスへ反映する | あり。許可されたインデックス取得・指定範囲の照会・必要な書戻しを行う | GUIの独立した実ストア照合操作、CLIの独立コマンド `reconcile` |
| 取得 / Fetch | 保存先のS3インデックスファイル自体を取得する内部処理 | あり | 再照合またはデータ操作の、許可された準備経路でだけ使用する |

- GUIには再読込と再照合の両方を提供し、どちらも単独の「更新」とだけ呼んで混同させない。再照合が取得済みインデックスだけを使って完了したことにせず、実データの正本を照会する。取得したS3インデックスも、実データ更新の実行可否判断の根拠にはしない。
- CLIは設計D-01〜03によりreconcile・restoreを最上位コマンドとし、GUIは独立起動とする。共通用語とコマンド構文の対応は下記およびCLI/GUI設計に記す。

### CLI・GUIの起動形式（2026-11-21、設計D-01〜03確定）

- CLIはcp・ls・reconcile・restore・rm・cfgを最上位コマンドとする。reconcileは独立した再照合で、一覧は出さず結果件数を返す。restoreは最上位へ置き、旧計画のch restoreとls --update-indexを別名として残さない。
- GUIの独立起動コマンドは `private-archive-gui`。`--config`・`--index-location`・`--data-class`・`--restore-tier`・`--ignore`・`--log-level` を受け、設定ファイルと既定値を実行時に上書きできる。引数なしで通常起動できる（設計D-03確定）。
- macOSでは、個人のMacで使う `.app` を簡単に生成・起動できる形を目指す（2026-11-21追加指示）。既存の設定・AWSプロファイルを再利用し、アプリ用の追加設定を増やさない。具体的なバンドル生成・起動ラッパー・署名・実機起動確認はGUI設計とP3-09/P3-10へ含める。
- lsはローカル参照専用。JSON提供もlsだけという既存契約を維持する。
- restoreの期間・方式等はURI列より前、再帰・深さはURIごと、という確定済みの適用規則を維持する。
- GUIは独立した `private-archive-gui` とし、`--config`・`--index-location`・`--data-class`・`--restore-tier`・`--ignore`・`--log-level` で共有設定を一時上書きできる。引数なしでは設定ファイルと既定値を使う。
- macOSでは、追加の面倒な設定を要さないローカル利用向け `.app` 化も目指す。既存AWSプロファイル・外部認証ラッパーの方針を維持して、具体的なbundle生成・起動方法をGUI設計へ落とし込む（設計D-03の追加指示）。

## インデックスと外部変更

- インデックスは、コスト低減のための実データの状態・操作結果の写しである。ローカル保存でもS3保存でも、実データの正本やトランザクションの管理元としては扱わない。
- インデックスが常に最新であることは要求しない。インデックスの保存成功と、要求された実データ操作の成功は区別する。
- インデックスファイルの保存先を設定で管理する。
- 保存先はローカルパスに加え、S3上のオブジェクトも指定できるようにする。
- 既定の保存先はローカルとする。リモート保存は選択可能な構成とする。
- `ls` はローカルインデックスだけを参照し、初回・再帰・詳細表示を含めS3 APIを発行しない。S3上のインデックス自体のHEAD・GET等も行わない。
- 実データ取得を除く通常の参照は、インデックスのqueryだけで完結させる。詳細表示も含め、管理対象の実オブジェクトへ鮮度確認のHEAD・LISTを自動発行しない。
- S3保存時はローカルコピーを保持する。インデックス自体の変更確認・取得を行えるのは、更新系操作または再照合（CLIの `reconcile`、GUIで指定ディレクトリ配下を更新する操作）の要求時だけとする。通常の `ls` やGUIの閲覧・ローカル再読込ではローカルコピーの古さを許容する。
- この確認の対象はインデックス1個であり、管理対象実オブジェクトの状態確認とは区別する。保存済み情報が古いこと自体は許容する。更新系操作での確認・取得失敗はwarningとし、要求操作を止めない。
- CLI 以外によるリモートオブジェクトの追加・変更・削除を想定する。
- 再照合は独立コマンド `reconcile` で明示実行する。lsへリモート照会のオプションを混在させず、旧計画の--update-indexを別名として残さない（2026-11-21、設計D-01確定）。
- 通常の `ls --recursive` はインデックスに記録済みの対象だけを列挙する。
- `reconcile` は指定URIと再帰・深さに応じた範囲を実ストアで照会し、インデックスへ反映して結果件数を表示する。一覧が必要なら続けてlsを明示実行する。
- 再照合は指定範囲の外部追加・変更・削除を反映する。範囲外の情報を再走査・更新しない。
- プログラムが全管理対象を把握することは前提にしない。CLIでは操作者が必要なURIを指定して再帰的に再照合する。GUIのトップレベルからの再照合は、そのインデックスに記録済みのバケットという限定された対象を使い、全アカウント・全管理範囲を自動発見する機能にはしない。
- 更新系操作は、指定範囲の実ストア情報を先に取得してインデックスへの反映を試み、その実ストア照会結果で実行可否を判定して実行し、成功した操作結果もインデックスへの反映を試みる。照会結果の利用をインデックスへの保存成功に依存させない。
- 更新時の対象選択を、事前に保存されていたインデックスだけで済ませない。指定範囲にある外部追加ファイルも実ストアの列挙結果に従って扱う。
- 更新系操作に伴うインデックス更新は、指定範囲の事前照合と、その要求操作の結果だけを対象にする。無関係な範囲を全走査しない。
- 操作対象外の外部変更が、通常のローカル参照に即座に反映される保証はない。
- インデックスに配置元のローカルファイルパスを保存する必要はない。
- 更新系操作では、インデックスに関する取得・読み取り・初期化・事前反映・結果反映・保存等のエラーはwarningとする。ローカルコピーを利用できない場合も、インデックスの成否は要求操作の実行判断や正常終了・エラー終了を決めない。
- `reconcile` およびGUIの再照合では、リモート状態の取得とインデックス更新そのものが要求操作であり、その更新を完了できなければ失敗とする。CLIはエラー終了し、GUIは操作の失敗を通知する。
- ローカルの既定パスは~/.private-archive/index.db。S3インデックスの書戻し単位・競合時の利用者向け契約は下記の確定事項、port/adapter・キャッシュ・取込等は[詳細設計](PHASE2_3_DESIGN.md)に従う。
- ローカルDBはbundled SQLiteを採用済み。保存先非依存のport、変更検知・スナップショット・共有作業DB取込の方式も設計へ確定した。

### S3インデックスの保存・競合（2026-11-20確定）

- ローカルインデックスは取得済み情報・操作結果を随時反映する。S3への書き戻しは、変更があれば1コマンドの終了時に1回まとめて試みる。オブジェクトごとや一定間隔の中間書き戻しは行わない。
- 要求操作の途中失敗・Ctrl+C時も、収束予算内で反映済み情報・確認済み成功分の書き戻しを試みる。最初の停止からの予算を延長せず、強制終了・電源断後の未送信分の回復まで保証しない。実データの成功済み操作をロールバックしない。
- 別プロセス・別PCによるS3インデックスの更新と競合した場合、他の更新を無条件で上書きせず、その実行内で競合を通知して終える。自動マージ・自動再試行はしない。ローカルに反映できた情報は通常の参照用コピーとして残せるが、未送信分の永続管理・再送キュー・専用の競合復旧機能は設けない（質問19の追加指示で明確化）。
- 競合・書戻し失敗は、cp・rm・復元では付属インデックスのwarningであり、要求操作の成否を変えない。再照合では要求された保存を完了できないエラーとする。ローカルの反映済み情報は残す。
- 通常の一覧・GUI閲覧ではS3同期を開始しない。次回の更新系操作では、その実行で取得した実ストア情報だけを対象選択・実行可否判断に使う。ローカル・S3インデックスの保存済み情報や前回の同期成否を、実データ更新の前提にしない。インデックス取得が許可される経路で参照用コピーを更新する際、前回未送信分の保護・復旧を必須手順にしない。
- 実行タイミングに依存する準備・回復・再送の管理を利用者へ要求しない。その実行で取得した情報はその実行の中で使用・反映を試み、失敗は同じ実行内で通知する。途中manifest等は実行内の一時情報であり、後続実行の操作履歴・途中再開・復旧状態として再利用しない（2026-11-20、質問19の追加指示）。

### 保存先とファイル形式の独立（2026-11-22、D-07確定）

- 同じDB adapterのインデックスファイルは、ローカル保存とS3保存で同一形式にする。S3専用のヘッダ・包み形式・必須の付随ファイルを追加しない。
- 正常に閉じた整合済みローカルDBを `aws s3 cp` 等でS3へコピーし、`index.location` をそのURIに変更すれば、更新系操作・再照合でそのまま取得して使える。S3からローカルへコピーし、保存先をそのパスに変更しても使える。保存先間の変換・アプリ専用の移行操作は不要とする。
- 既存の参照契約は維持する。S3へ切り替えた直後でも、通常ls・GUIの起動/閲覧/再読込は自動取得しない。ローカルに写しがなければ、最初の明示的な再照合等で取得する。
- DB形式・シリアライズ/デシリアライズ・整合済みファイルの生成/検査はDB adapterへ閉じ込め、portを介して利用する。SQLiteからredb等へのadapter差し替えでコアの業務判断を変えない。異なるDB形式間のファイル自動変換は保証しない。
- indexクレートは保存先がローカルかS3かを判断せず、ETag・条件付きGET/PUT・転送キャッシュを所有しない。S3の変更検知・競合制御は保存先adapter側の責務とし、転送用メタデータをインデックス本体へ埋め込まない。
- 転送キャッシュやETagがなくても、DBファイル単体を利用できる。条件付き取得は、保存先adapterが対応付けを保証できる取得済みファイルにだけ使う最適化とする。

### 保存先切り替え・手動再作成（2026-11-20確定）

- `index.location` の変更は使用するインデックスの切り替えだけとする。旧インデックスを自動コピー・統合・削除せず、設定操作だけでリモート照会しない。切替先が未作成なら未作成時の既存契約を使う。
- 移行・破損復旧は明示手順で行う。必要なら全利用プロセスを閉じて既存ファイルを退避し、別の正常な保存先・新規保存先を選んで、必要なURIだけ `reconcile` で再照合する。全範囲の自動発見・過去操作の再生を必要とする仕組みにしない。
- 未対応のDB形式・スキーマは詳細を伴うエラーとし、正常な既存インデックスを黙って空に置き換えない。別DB形式・将来の未対応スキーマの自動変換は今回提供しない。

### 使用中S3インデックスの通常データ操作（2026-11-20確定）

- 使用中のS3インデックス自身が `cp`・`rm`・`restore` の選択対象となる場合、実データ操作の開始前にエラーとする。全対象の解決・ignore適用後に判定し、含まれる場合は他の対象への実データ操作も始めない。cpは解決したコピー元・宛先の双方を判定する。
- インデックスを別バケット・操作範囲外へ配置するか、ignoreで明示除外することで通常のデータ操作を実行できる。インデックス用の暗黙ignoreは追加しない。アプリ内部の正規インデックス保存は通常のデータ操作と区別する。

### 未作成・破損時の動作

- ローカルインデックスが未作成なら空のインデックスを自動作成できる。S3保存設定でも、ローカルコピーの初期化だけを理由にS3へアクセスしない。
- `ls` で利用可能なローカルコピーがなければ、空の結果を返し、対象0件として終了コード `1` にする。初回でもリモートインデックスの取得や実オブジェクトの列挙を自動実行しない（2026-11-20、対象なしはエラーという追加方針を適用）。
- 更新系操作または再照合が要求されたときに限り、S3インデックスの確認・取得と指定範囲の実ストア照会を実施できる。GUIの起動・フォルダ選択・ローカル再読込も、空のローカルコピーを理由に自動取得しない。空のローカルコピーだけから、S3上にもインデックスが存在しないと判断しない。
- インデックスの破損を検出したら、特定できる箇所・原因の詳細をコアから返してCLIで表示する。通常の `ls` で問い合わせ不能、または `reconcile` で要求された更新不能ならエラー終了する。更新系操作では破損もインデックスのwarningとして扱い、要求操作を継続する。箇所を特定できない場合も、判明している情報を表示する。
- 破損時に自動再構築・実ストアの再走査を行わない。破損を未作成と見なして空に置き換えない。S3 API課金が発生する修復処理を暗黙に開始しない。

## 設定ファイル

- ユーザ単位の設定ファイルを使う。
- 設定形式はTOML、既定パスは `~/.private-archive/config.toml`。`--config PATH` で使用する設定ファイルを変更できる。
- 設定ファイル未作成時は組み込み既定値で動作する。ファイルの作成はCLIの `cfg` の作成系コマンド、またはGUIの明示的な設定操作で行い、通常の参照・データ操作で暗黙に作成しない。
- 設定可能な全項目を `cfg` から更新できること。構文は `cfg`、`cfg init`、`cfg get KEY`、`cfg set KEY VALUE`、`cfg unset KEY` とし、詳細は [CLI要件](cli/REQUIREMENTS.md) に記す。
- インデックス保存先を設定項目に含める。設定項目はすべて実行時にも指定可能にする。
- 値は「組み込み既定値 → 設定ファイル → 実行時の明示指定」の順に上書きする。優先度は実行時指定が最も高い。
- 実行時の明示指定を必須にした項目は、組み込み既定値を持たせず、設定ファイルの管理対象にも含めない。復元保持期間はこの区分に含める。
- 設定キー・値・パス解決はCLI要件と確定済み設計を正本とする。CLI・GUIの具体的な引数構文はD-01〜03と各設計で確定済み。
- 共通のignoreパターンを設定ファイルで指定できること。実行時の `--ignore` 指定がある場合は設定値を置き換える。
- `--ignore ""` は、そのコマンドに限りignoreによる除外を無効にする。設定ファイル自体は変更しない。
- 設定ファイル自体はローカルに置く構成で検討する。リモートインデックスの保存先とは別に扱う。
- GUIにも設定値を更新するUIを今回の完成範囲として含める。CLIと同じ設定ファイル・値の検証契約を用い、設定操作自体ではS3照会やインデックス移行を行わない。設定作成・保存・キャンセル・項目を既定値へ戻す操作を提供し、保存は次の操作から適用する。起動引数による上書きは維持する。専用の一時設定UIは作らず、起動引数の具体形式は設計で相談する（2026-11-21確定）。

## CLI出力

- 要求操作の結果は標準出力（stdout）に出す。
- warning・エラー・進捗は標準エラー出力（stderr）に出し、stdoutへ混在させない。
- JSON出力時のstdoutにはJSONだけを出す。warning・エラー・進捗はこの場合もstderrに出し、パイプ先が結果を解析できるようにする。
- JSON配列の逐次出力中に要求操作が失敗した場合は、出力済みの結果を配列として閉じ、エラーをstderrに出して非ゼロの終了コードで終了する。JSONの構文が正常でも結果が一部だけの場合があり、完了したかどうかは終了コードで判断する。stdoutへの書き込み自体が不能な場合や強制終了時のJSON完成は保証しない。
- 出力は逐次処理を前提とする。JSON出力は今回 `ls --json` のみ提供し、キー・値の表記は下記の2026-11-20確定契約に従う。cp・rm・復元・cfgは確定済みの通常表示を提供する。これらのJSON出力は今回の完成範囲に含めない。
- 削除成功は対象URIを1件ずつstdoutへ出す。復元要求の成功は対象URI・要求日数・方式を「受付済み」として1件ずつstdoutへ出し、復元完了と区別する（2026-11-19確定）。
- CLIの進捗はstderrが端末で、infoが有効な場合だけ表示する。パイプ・ファイル等へ向くstderrには進捗を出さない。error・warn指定時は進捗も抑制する（端末条件は2026-11-19、ログとの整合は2026-11-20のログ契約を反映）。

### 全CLIの終了コード（2026-11-19確定）

| 結果 | 終了コード |
| --- | --- |
| 正常完了・warningのみ | `0` |
| 要求処理の失敗・成否不明 | `1` |
| 引数・設定値の不正 | `2` |
| Ctrl+Cによる中断 | `130` |

- `rm` の確認で `yes` 以外、または入力終了（EOF）になった場合は、削除を始めず `1` で終了し、再入力を求めない。
- 正常完了・失敗・中断の判定は出力の有無と区別し、ログレベルを変えても変わらない。cpの既存の停止原因・確定成功の判定を維持する。

### 対象0件（2026-11-20、2026-11-21のD-04〜06を反映）

- CLIの `cp`・`ls`・`rm`・`restore` は、範囲・深さ・ignore適用後の対象が0件なら「要求操作を実施できない」エラーとして `1` で終了する。不存在、空の再帰配下、全件ignoreを含め、全件ignoreを正常終了とした旧契約を上書きする。
- `ls` は引数なしのルート一覧・未作成インデックス・通常検索も同じく0件なら `1`。JSON時は空配列を出し、エラーはstderrに出す。対象なしを補うための自動リモート照会は行わない。
- 一部をignoreしても、残った対象の要求処理をすべて完了できれば正常終了とする。除外された対象を含めるために範囲を拡張したり、ignoreを自動解除したりしない。
- 削除対象0件なら承認入力へ進まずエラー終了する。取得済み反映・成功済み処理を、対象0件等によるエラーを理由にロールバックしない。
- `reconcile` とGUI再照合は、指定範囲の照会を正常に完了し、有効範囲が空だと確認・反映できた場合は成功とする。開始時revision・範囲・深さ・ignoreの既存規則に従い、削除済みの古い記録を除去できる。権限・通信・保存失敗を空範囲と見なさない（D-04確定）。
- 全件ignoreで有効な対象の状態を確認できない再照合はエラーとする。除外されたことを削除の根拠にせず、全件ignoreの失敗では削除照合へ進まない。ignore発生と確認済み除外通知件数をinfo、個々のURI・パスをdebugで出す。除外ディレクトリ配下の未走査ファイル数は推測しない（D-06確定）。
- cfg・help等の対象オブジェクトを列挙しないコマンドに、ファイル件数0によるエラーは適用しない。GUIの起動・閲覧・再読込の0件は空の列を表示する。既知バケット0件でGUIトップレベルの照合範囲自体がない場合は失敗を通知し、S3を照会しない。

### CLI再照合の範囲（2026-11-21、D-05確定）

- `reconcile URI` は1つのURIを必須とし、非再帰は完全一致の1件を照会する。配下の照合には `--recursive` を明示し、深さは `--recursive-depth N` で制限する。深さだけの指定・0は入力エラー。
- バケット全体の照合には `--recursive` を使う。保存済みインデックスを見て非再帰の照合範囲を自動拡張しない。GUIで選択したフォルダの既定再帰・深さ無制限は維持する。

### ログレベル（2026-11-20確定）

- オプション引数 `--log-level` で `error`・`warn`・`info`・`debug`・`trace` を指定できる。組み込み既定値は `info`。指定レベル以上の重大度のログ・診断をstderrへ出し、通常結果・JSONのstdoutには混在させない。
- 設定キーは `logging.level` とし、TOMLの `[logging] level = "info"` 等で保存可能にする。優先順位は組み込み既定値 → 設定ファイル → `--log-level`。cfg・GUIからも他の設定と同じ契約で編集できる。未知のレベル値は入力エラー `2`。
- 開始・終了・集計等を `info`、再帰でignoreされた個々の対象URI・パスを `debug` とする。直接指定した対象がignoreされた場合は既存契約どおり `warn`。ignoreの発生と確認済み除外通知件数をinfoの集計で示す。未走査配下のファイル数を推測せず、ログのために除外範囲を走査しない。個々の除外を通常時にすべてwarningとして出し続けることは要求しない。
- `error` 指定ならwarning以下を、`warn` 指定ならinfo以下を抑制する。結果stdout・要求操作の成否・終了コードはログ抑制で変えない。対象0件エラーは、ignore詳細を抑制していてもerrorとして通知する。
- ログ出力のための追加リモート照会は行わない。ログは型付きDiagnosticと非同期sinkで接続し、グローバルな同期loggerを追加しない。詳細は[実装設計](PHASE2_3_DESIGN.md)に従う。

### lsの詳細表示・JSONの基本項目

| 項目 | JSONキー | 意味 |
| --- | --- | --- |
| URI | `uri` | 対象を識別するURI |
| 種別 | `kind` | オブジェクト・ディレクトリ相当・ストアルートを区別する情報 |
| サイズ | `size_bytes` | 記録されているデータサイズ |
| 保存クラス | `data_class` | 記録されている保管クラス。復元状態とは区別する |
| 復元状態 | `restore_state` | 最後に取得・記録した復元状態 |
| 復元期限 | `restore_until` | 取得・記録できた復元一時コピーの有効期限 |
| 元の更新日時 | `original_mtime` | 元ファイルの更新日時。S3のLast-Modifiedで代用しない |
| 元の作成日時 | `original_creation_time` | 元ファイルの作成日時 |
| UNIX権限 | `unix_mode` | 記録できた元ファイルのUNIX権限 |
| 最終照会日時 | `queried_at` | 対象の実ストアの情報を最後に照会した日時。表示やインデックスの取得日時とは区別する |

- `ls --detail` とJSON出力は上記を基本項目とする。未取得の情報は「不明」として扱い、推測した既定値で埋めない。JSONの不明値は `null` とする（2026-11-20確定）。
- 表示項目を埋めるための追加リモート照会は行わない。インデックスが持つ情報を表示し、照会済み情報が古い場合も自動更新しない。
- 通常のls・ローカルDBの問い合わせ・S3インデックスの取得だけで、対象の最終照会日時を新しい時刻へ進めない。最終照会日時は各対象の実データ情報の照会時刻を表す。
- CLI一覧の既定はURIの昇順とし、大文字小文字を区別する。OSの言語・地域設定で並び順を変えず、ディレクトリを別枠で先頭に集める並べ替えは行わない（2026-11-20確定）。
- CLIの `ls --sort` とGUIのソート操作を提供する。カンマ区切りの複数条件を左から優先し、同じ値の中で次の条件を使う。対応値・不明値・同値時の規則は下記「一覧のソート」に従う（2026-11-22、D-09a〜c確定）。表示順の指定でrm・restoreの実行順を変えない。
- 通常表示は1行1URI、`--detail` は基本10項目を表示する。`--json` はstdoutの結果をJSONにする表示オプションであり、`--detail` の有無によらず全10項目を出す。設定ファイルはTOMLのまま。結果JSONと設定形式は別の契約として扱う。
- ディレクトリ相当・ストアルートのサイズ・保存クラス等は、配下を集計せず不明として表示する。実在するオブジェクト自体のサイズ等と、prefixから導出したディレクトリの値を混同しない（2026-11-20確定）。

### 一覧のソート（2026-11-22、D-09a〜c確定）

| enumの外部表記 | ソート対象 | 方向 |
| --- | --- | --- |
| `name-asc` | 末尾の名前 | 昇順 |
| `name-desc` | 末尾の名前 | 降順 |
| `size-asc` | 記録されたバイト数 | 昇順 |
| `size-desc` | 記録されたバイト数 | 降順 |
| `uri-asc` | フルURI | 昇順 |
| `uri-desc` | フルURI | 降順 |

- `--sort size-asc,name-desc` はサイズ昇順、同サイズなら名前降順。`--sort name-desc,size-asc` は名前降順、同名ならサイズ昇順。先に指定した条件ほど優先する。
- 名前・URIは大文字小文字を区別し、言語・地域設定に依存しない文字順とする。数値を自然順に解釈する追加規則は設けない。
- 未指定時は `uri-asc`。不明値は昇順/降順とも最後。全指定条件が同じならURI昇順を使い、順序を安定させる。ディレクトリ/ルートのサイズをソート用に合算しない。
- CLIは通常/詳細/JSONとも今回の一覧結果全体をソートし、再帰時にも結果全体に同じ条件を適用する。GUIは各列の直下項目を同じ条件でソートする。
- GUIは条件と方向の追加・削除・優先順位変更を提供する。選んだ条件は起動中だけ保持し、設定ファイル・起動履歴へ保存しない。ソート変更はローカル問い合わせだけで行い、S3を照会しない。
- CLI/GUIは同じenumとソート定義を使う。日時等の追加キーは今回含めない。全結果のメモリ保持を前提にせず、既存の件数・メモリ制約を守る。

### lsの結果JSON表記（2026-11-20確定）

- キーは上記のsnake_caseで固定し、各要素に全10キーを必ず出す。不明値をキーの省略・空文字列・0で代用せず `null` とする。
- 日時はUTCのRFC3339文字列（末尾 `Z`）とし、取得・保持できた小数秒を失わない。元の更新日時・作成日時・復元期限・最終照会日時に同じ表記を用いる。
- サイズはバイト単位のJSON整数。人向け単位付き文字列へ変換しない。UNIX権限は `"0755"` 等の8進数文字列とする。
- 種別は `object`・`directory`・`root`、保存クラスは既知の `standard`・`archived` または記録できたその他のストア固有クラス名とする。不明な保存クラスは `null`。復元状態は次の表に従う。
- 配列の逐次出力・途中失敗時の終端処理・stderr分離・終了コードによる完了判定は既存の契約を適用する。通常表示の書式と結果JSONのデータ表記を混同しない。

### 復元状態の表示（2026-11-20確定）

| 表示上の区分 | `restore_state` のJSON値 | 意味 |
| --- | --- | --- |
| 不要 | `"not_required"` | 照会時点で復元不要と確認できた状態 |
| 未復元 | `"archived"` | 照会時点でアーカイブされ、復元中・復元済みではない状態 |
| 復元中 | `"restoring"` | 最後に取得・記録した復元処理中の状態 |
| 復元済み | `"restored"` | 最後に取得・記録した復元済みの状態 |
| 不明 | `null` | 状態を取得・確定できていない状態 |

- 通常一覧は最後に取得・記録した状態を示す。保存済み復元期限が現在時刻を過ぎても、時計だけで状態・最終照会日時を書き換えない。復元期限と最終照会日時を詳細・JSONで併記し、保存済み情報であることをhelp等で説明する。
- 現在の実状態は再照合、または要求操作に必要な事前照会で確認する。通常一覧での追加API・自動ポーリングはしない。保存クラスと復元状態を別項目として維持する。

## ファイル・メタデータ・ignore

- 指定ファイルをそのまま出し入れする。自動圧縮、展開、複数ファイルの自動集約は行わない。1ファイルを1オブジェクトとして扱う。
- 操作対象として残ったシンボリックリンクはエラーにする。リンク自体の保存・復元やリンク先の自動追跡は行わない。
- 空ディレクトリの保存・復元は要求しない。
- 内容を転送するコピー操作の正常終了は、データ内容を転送できたことを必要十分条件とする。属性の保持・復元成功を条件に加えない。
- ファイルの更新日時、作成日時、UNIX権限はbest effortで保持・復元する。所有ユーザ情報は保持しない。
- 保存できた元の属性は、指定範囲のインデックスを再構築した場合も可能な限り保持する。インデックスを属性情報の唯一の正本にはしない。具体的な保存方法は設計段階で決める。
- 非対応OS・ファイルシステム、権限不足、属性のない外部配置オブジェクト等は、取得・設定できる情報だけを扱う。属性不足・保持失敗はwarningとし、内容の転送が成功していれば正常終了する。
- アクセス日時、ACL、拡張属性、所有グループ等の追加属性を必ず保持する要求はない。
- ignoreに一致したファイルは、ローカル・リモートを問わず、一覧表示、再帰列挙による処理対象、コピー、削除、復元等の操作対象にしない。
- ignoreは各コマンドに共通して適用し、インデックスに既に記録されている対象も `ls` の表示から除外する。
- ignoreで除外されたシンボリックリンクは操作対象に含めず、リンクを検出したことによるエラーも発生させない。
- ignoreのパターン記法はgitignoreと同様にする。ワイルドカード、`**`、ディレクトリ指定、`!` による再包含、順序による判定を扱う。
- `.gitignore` やGitの設定・リポジトリ状態を参照しない。除外ルールの取得元は本アプリの設定ファイルと実行時指定のみとする。
- ローカルの照合基準はCWD。リモートの照合基準はコマンドで指定された操作対象とする。
- 例: `ls s3://bucket/path/to --recursive` では `path/to` を基準とした相対パスでignoreを検証する。バケット直下を固定の基準にはしない。
- 操作対象やCWDを変えると同じファイルでも除外結果が変わりうる。この性質はhelp等に記述上の注意として示し、CLIで基準を超えた恒久的な保護対象の管理は行わない。
- ignoreの組み込み既定値は空。`.DS_Store` 等も自動で組み込まず、操作者が設定する。
- 再帰指定時の既定動作は、隠しファイル・隠しディレクトリ配下も含め、指定範囲・深さの全ファイルを走査対象にする。`.DS_Store` と `.git/` も対象とし、先頭のドット・Git管理下・OS生成ファイルであることを理由に暗黙には除外しない。無視するには設定のignore、またはその実行の `--ignore` による明示指定が必要（2026-11-19、ユーザの「ls -a」の意図を確認して確定）。対象種別の制約、symlinkを追跡しないこと、走査失敗時の即時停止は既存契約に従う。「走査可能」はアクセス不能を黙ってスキップする意味にはしない。
- 実行時は `--ignore '*.tmp,.DS_Store'` のようにカンマ区切りで複数指定する。指定された一覧で設定ファイルの一覧全体を置き換え、結合はしない。
- ignoreは誤操作防止にも使う。対象をパスで直接指定しても有効なignoreを優先し、warningを出してスキップする。一時的に参照・操作したい場合は実行時にパターンを変更・解除する。
- ignoreに一致する対象をインデックスへ新たに取り込まない。既存レコードは保持するが、有効なignoreに従って表示・操作対象から除外する。ignore設定だけの変更を実データの削除や既存レコード削除として扱わない。
- ignoreを解除した場合、既存レコードは再び表示できる。除外中に取り込まれなかった対象を通常のlsが自動発見することはなく、指定範囲の `reconcile` による再照合が必要となる。
- 単一ファイルのignore基準とコピー先への適用は下記cp契約で確定。カンマ自体を含むパターンはTOMLのリストで表せる。cpの実装前にユーザ確認し、CLIでは `\,` を文字としてのカンマ、`\\` を文字としてのバックスラッシュとして扱う。その他のバックスラッシュはgitignore記法のため保持する。

パターン構文の参照先: [Git gitignore documentation](https://git-scm.com/docs/gitignore)。
参照するのはパターン記法のみであり、Gitの管理・設定の仕組みは導入しない。

## データ操作

- Phase 1 の `cp` はローカル→S3、S3→ローカル、S3→S3の3方向を提供する。
- loader・saverの許可する組み合わせをenumで列挙し、対応する実装をtraitで要求する案は設計段階の検討材料として記録する。具体的な型・実装方式はまだ確定しない。
- コピー先が存在しない場合は新規作成、存在する場合は上書きする（`aws s3 cp` と同じ意図）。
- Phase 1 で旧バージョンの選択・履歴管理は要求しない。コピー中断時の扱いは下記「Phase 1 cpの確定契約」に従う。
- クラス指定は `standard`（S3 Standard）・`archived`（S3 Glacier Deep Archive）。プログラム組み込みの既定値は `standard` とする。
- 保存クラスの既定値は設定ファイルで変更でき、`cp --data-class` でその操作だけ指定できる。優先順位は実行時指定、設定値、組み込み既定値の順とする。他ストアへの対応付けは今回の完成範囲外。
- 即時取得できないアーカイブオブジェクトへのダウンロードはエラーにする、という memo の前提で検討する。
- 復元要求・復元状態の確認・削除・再帰操作を提供する。
- 復元方式の組み込み既定値は `Bulk` とし、設定ファイルおよび実行時に変更できる。保持期間の実行時必須指定とは別の項目として扱う。
- 復元保持期間は実行時の明示指定を必須にし、既定値を持たせない。設定ファイルの値で省略を補完しない。
- 復元期間は正の整数に `d`（日）または `w`（週）を付けて指定する。`7d` は7日、`1w` は7日として扱い、記法と例をhelpに表示する。
- `32h` 等の時間表記はエラーにする。日数への自動切り上げはしない。
- 復元要求は受付とその結果のインデックス反映を終えたら終了し、復元完了まで待機・自動ポーリングしない。
- 復元中・復元済み・Standard等の即時取得可能なオブジェクトへの復元要求はエラーにし、共通の即時停止方針に従う。warningでのスキップや、復元済みコピーの期限変更としては扱わない。事前照会結果で判断できる場合は復元APIを送信する前にエラーにする。
- 状態確認は操作者が `reconcile` を外部のループや待機処理と組み合わせて行う。今回のCLIに復元完了待機機能は要求しない。
- 再アーカイブ専用操作 は提供しない。復元一時コピーの解放・保持期限短縮の専用コマンドも要求しない。復元時に明示した期間の期限切れに任せる。
- `rm` は実対象の列挙・ignore適用後、削除を開始する前にコマンド全体で1回確認する。指定URI・対象件数・合計サイズを表示し、memoどおり `yes` だけを承認として受け付ける。`--auto-approve` で確認を省略できる。要求操作の失敗時と発行済み処理の扱いは、下記「削除・復元の実行と中断」の確定契約に従う。
- `--auto-approve` のない `rm` は、標準入力が端末であることを確認の前提とする。パイプ・ファイル・`/dev/null` 等からの承認入力は受け付けず、読み取りを始めずにエラー終了する。この条件は実対象のリモート照会前に判定し、無用なS3アクセスを発生させない。
- `--auto-approve` があれば標準入力から承認を読まず、端末でない場合も実行できる。これは承認入力の制約であり、stdoutをパイプ・リダイレクトすることは制限しない。パイプの拒否を実現するためのreadタイムアウトは必要条件にしない。

### パス・再帰の確定事項

- `cp`・`rm` のパス解釈・操作対象の選択・コピー先への配置は `aws s3` に合わせる。既に合意したignore、削除確認、即時停止・自動リトライなし、属性のbest effort保持等の共通要件は引き続き適用する。AWS CLIの全オプション・既定動作への互換性を要求するものではない。
- 非再帰の `ls` は指定対象に完全一致するオブジェクトを表示する。対象がディレクトリ相当であればディレクトリであることを示し、子の一覧へ自動展開しない。
- 同名の完全一致オブジェクトと配下のprefixが共存する例では、`ls s3://bucket/foo` は完全一致する `foo` を優先する。
- `cp`・`ls`・`reconcile`・`rm`・`restore` の `--recursive-depth` は `--recursive` の併用を必須とし、単独指定と深さ0は入力エラーにする（2026-11-19、残るコマンドにも適用することを確定）。復元ではURIごとにこの条件を検証する。再帰の深さは指定箇所からの階層数とする。`foo/` を起点とする深さ1は `foo/a.txt`、深さ2は `foo/sub/b.txt` まで。深さの指定がなければ制限しない。
- `cp` のパス解釈はAWS CLIに合わせる。非再帰では単一ファイル・オブジェクトをコピーし、コピー先がS3のキーを持つURIなら末尾 `/` なしは指定キー、ありはコピー元のファイル名を追加したキーに保存する。
- コピー先が既存のローカルディレクトリなら、末尾 `/` がなくてもディレクトリとしてコピー元のファイル名を追加する。
- 再帰コピーはコピー元のディレクトリ・prefixの中身を、相対階層を保ってコピー先の配下へ配置する。コピー元ディレクトリ名を自動で1階層追加しない。
- 再帰コピーではコピー元・コピー先の末尾 `/` の有無で配置結果を変えない。

| コピー例 | `photos/a.jpg` の保存先 |
| --- | --- |
| `cp photos s3://bucket/backup --recursive` | `s3://bucket/backup/a.jpg` |
| `cp photos/ s3://bucket/backup/ --recursive` | `s3://bucket/backup/a.jpg` |
| `cp photos/a.jpg s3://bucket/backup` | `s3://bucket/backup` |
| `cp photos/a.jpg s3://bucket/backup/` | `s3://bucket/backup/a.jpg` |

根拠: [AWS CLIのパス規則](https://docs.aws.amazon.com/cli/latest/reference/s3/)、[cp](https://docs.aws.amazon.com/cli/latest/reference/s3/cp.html)、[パスの整形実装](https://github.com/aws/aws-cli/blob/develop/awscli/customizations/s3/fileformat.py)。

### Phase 1 cpの確定契約（2026-11-15）

P0-01の質問1〜9に対するユーザ回答を反映する。質問2は逐次転送案ではなく、転送前に再帰指定を具体的なURIへ解決する方針を採用した。

- **対象の事前解決**: 再帰コピーは指定範囲を最後まで列挙し、深さ・ignoreを適用して、具体的なコピー元と配置先の組を確定してから本文転送を始める。解決途中のエラー時は本文転送を開始しない。単一ファイルも同じ事前確認経路を使う。対象一覧は一時ディスクへ逐次記録し、全件をメモリに保持しない。
- **事前照会範囲**: コピー元の指定範囲と、解決した各コピー先だけを照会する。無関係な宛先prefixを走査しない。既存宛先は上書き候補、存在しない宛先は新規作成候補とする。権限エラー・通信失敗を不存在と解釈しない。必要なローカル親ディレクトリは作成するが、S3バケットの自動作成はしない。
- **実行判断とインデックス**: 実ストア照会結果を事前解決の一覧へ直接渡す。付属のインデックス反映が失敗しても解決・転送を続行できる。一覧作成そのものに必要な一時ディスクの失敗は要求操作のエラーであり、インデックスのwarningとは区別する。
- **事前解決後の変更**: 解決後に追加されたファイルは今回の対象へ追加しない。事前照会は転送成功を保証せず、その後の削除・変更・権限変更等で発生した実操作のエラーを返す。全体のスナップショットや実データの独自競合ガードは提供しない。
- **ローカル宛先の保護**: 宛先と同じディレクトリの一時ファイルへ書き、本文の受信・サイズと可能な内容検証・closeの成功後に宛先へ置換する。失敗・キャンセル時は既存宛先を残し、一時ファイルの削除を試みる。削除失敗は元のエラーにwarningを加える。未作成だった最終ファイルは公開しない。作成した親ディレクトリのロールバックは要求しない。強制終了・電源断時の一時ファイル削除や永続性までは保証しない。
- **S3宛先**: 完了前のmultipartの後始末を試みる。S3への書き込み要求を発行した後に応答を失った場合、未変更だったと保証せず、成否不明として通知する。成功済み宛先を元へ戻す処理はしない。
- **途中再開**: 今回は実装しない。再実行時は各ファイルの先頭からコピーし、残存パート・部分ファイルを再利用しない。
- **失敗・キャンセル**: 新規ファイル・新規パートの開始を止め、発行済み処理の終了確認と後始末を上限時間内で試みる。成功が確認できた結果の表示・インデックス反映を試みる。応答を確認できない処理は成否不明と通知し、正常終了にしない。成功分のロールバック・自動リトライは行わない。待機上限は設計で定める。
- **内容の検証**: 期待サイズと転送サイズ、利用可能なチェックサムを検証する。不一致や本文ストリームのエラーはコピー失敗。チェックサムがない外部配置オブジェクトはwarningで続行し、未検証の内容を検証済みとは表示しない。通常コピーの後に全本文を再ダウンロードすることは要求しない。実転送の受入試験では縮小サイズで内容一致を確認し、100GB相当は分割計算・制御経路で検証する。100GB実転送済みとは扱わない。ETagを常に本文ハッシュと見なさない。
- **特殊ファイル**: 通常ファイル以外のFIFO・ソケット・デバイス等は、ignoreされていなければエラーにする。ディレクトリは再帰列挙にだけ使う。シンボリックリンクは既定どおり除外済み以外はエラーとする。
- **単一対象のignore**: ローカルはCWD基準。リモートの単一キーは親prefix基準とし、`s3://bucket/photos/a.jpg` の直接指定では `a.jpg` と照合する。バケット直下の単一キーはバケットルート基準とする。再帰指定は指定prefix基準を維持する。
- **宛先のignore**: コピー元と、配置を解決したコピー先の双方に適用し、どちらかが除外対象ならスキップする。除外の通知レベルは上記ログ契約に従い、直接指定はwarn、再帰の個々の対象はdebugとする。リモートの再帰宛先は指定した宛先prefixを基準に相対配置先を照合し、単一宛先は解決後の親prefixを基準にする。ローカル宛先はCWD基準とする。除外対象の本文転送・新規インデックス取込はしない。
- **結果と終了コード**: 成功したファイルごとにコピー元・宛先・転送バイト数をstdoutへ逐次出力する。warning・エラー・進捗はstderr。cpの終了コードは成功（warningだけの完了を含む）`0`、処理失敗`1`、入力不正`2`、Ctrl+C`130`。成否不明は処理失敗、Ctrl+Cが原因なら`130`とする。2026-11-19に全CLIへ同じ終了コードを適用することを確定。2026-11-20、全件ignoreを含む対象0件は `1` に変更。JSON表記はP2-01で決める。

#### cpの受入例

- 再帰対象の2ページ目の列挙に失敗した場合、本文のPUT・GET・COPYはまだ開始されていない。取得済み情報の付属インデックス反映は残ってよい。
- 宛先に対応するキーが未作成なら新規作成する。宛先照会が403になった場合は不存在と見なさず、本文転送前に失敗する。
- 既存ローカルファイルへのダウンロードが途中で失敗した場合、元の本文は残り、一時ファイルの削除を試みる。成功時だけ置換される。
- 途中まで成功した再帰コピーを再実行すると、今回の全対象を解決し直し、各対象を先頭からコピーする。既存宛先を自動スキップしない。
- 直接指定した `s3://bucket/photos/a.jpg` はignoreの `/a.jpg` と一致し、本文を取得せずwarningでスキップする。
- コピー元が除外対象でなくても、解決後の宛先が有効なignoreに一致すれば転送しない。
- チェックサム不一致ならコピー失敗として停止する。チェックサムがない外部オブジェクトは、期待サイズの本文取得に成功すればwarning付きで成功する。
- 成功2件の後に失敗した場合、成功2件の出力を残して終了コード1で終了する。属性・インデックスのwarningだけなら0、Ctrl+Cなら130である。

### rmの対象（AWS CLI互換で確定）

次のキーがある場合を考える: `foo`、`foo/a.txt`、`foo/sub/b.txt`、`foobar/c.txt`。

- 非再帰の `rm s3://bucket/foo` は完全一致するキー `foo` だけを削除し、配下のキーは対象にしない。
- `rm s3://bucket/foo --recursive` はAWS CLIと同様、prefixを `foo/` として列挙する。削除対象は `foo/a.txt` と `foo/sub/b.txt` で、完全一致の `foo` と `foobar/c.txt` は含まない。
- `rm s3://bucket/foo/ --recursive` も同じ対象になる。
- 確認方法: 公式資料・公開実装を読み、インストール済みAWS CLI 2.18.3へlocalhostの模擬S3応答を返す `--dryrun` でrm 2ケース・cp 6ケースを確認。AWS上のリソースは操作していない。

### 復元保持期間・費用に関するS3制約（調査済み）

- Glacier Deep Archive の復元保持期間は整数の日数で指定し、最短1日。時間をそのまま指定するAPIはない。
- 期限は復元完了時刻に指定日数を加算した後、UTCの翌日0時へ切り上げられる。指定から厳密に何時間後、という期限は保証できない。
- CLIの `1w` はS3へ7日として要求する。`32h` は非対応の入力として拒否する。
- 復元済みコピーの期限は現在時刻を基準とする日数で変更できる。復元処理中は期限変更できない。
- 一時コピーはS3 Standardの保管料が発生し、復元済みオブジェクトへの再度の復元要求はGET相当のリクエスト料金がかかる。
- 確認できた期限変更手段は最短1日の再指定であり、復元コピーだけをその場で削除する操作としては扱わない。

根拠:

- [Working with archived objects: 有効期限の算出](https://docs.aws.amazon.com/AmazonS3/latest/userguide/archived-objects.html)
- [RestoreObject: 復元済みコピーの期間変更](https://docs.aws.amazon.com/AmazonS3/latest/API/API_RestoreObject.html)

### 複数対象の復元（採用・オプションの適用範囲を確定）

- S3の `RestoreObject` はオブジェクト単位のAPI。CLIの呼び出し回数を減らしても、同じオブジェクト集合への復元要求料金・データ量料金自体は減らない。
- S3 Batch Operations は処理対象ごとの操作料金に加え、ジョブ・処理オブジェクト等への追加課金がある。コマンドの複数URI対応とS3 Batch Operationsの採用は別の判断とする。
- 複数URIを1回の復元コマンドで指定できる。構文は `restore [全体オプション] URI [URIオプション] URI [URIオプション] ...` とする。
- 復元保持期間・復元方式等の全体オプションはURI列の前に置き、全対象へ適用する。保持期間は引き続き実行時必須である。
- `--recursive`・`--recursive-depth` はURIごとに指定する。各URIの直後から次のURIまでの指定をそのURIに適用し、別のURIへ引き継がない。再帰指定がないURIは非再帰として扱う。
- 例: `restore --restore-duration 7d s3://bucket/photos --recursive --recursive-depth 2 s3://bucket/video.zip s3://bucket/docs --recursive`。保持期間は全対象7日、photosは深さ2まで、video.zipは完全一致、docsは深さ制限なしの再帰とする。
- 復元の再帰対象はcp・rmと同じ規則とする。指定 `foo`・`foo/` はともに `foo/` 配下を対象とし、キー `foo` 自体や `foobar/` 配下は含めない。深さは指定箇所の直下を1とする。
- 復元要求を送る前に、指定された全URIを各URIの再帰・深さ・ignoreに従って具体的なオブジェクトのキーへ解決し、同一ストア・バケット内の同じキーを重複排除する。同一URIの重複と重なるprefixの双方を扱い、異なるバケットの同名キーは別対象とする。
- 全URIの解決・重複排除が完了してから復元要求を開始し、同じオブジェクトへの要求は1コマンドにつき1回だけ送る。解決中の失敗時には復元要求を開始しない。事前照会によるインデックス反映は実データ操作と区別する。
- 解決済みキーの重複排除でも、対象件数に比例するメモリ保持を要求しない。具体的な保存・重複排除の実現方式は設計段階で決める。
- 重複排除後の処理順序はURIの指定順を優先し、各URI内はキーの昇順とする。同じオブジェクトは最初に出現するURIの位置で1回だけ処理する（2026-11-19確定）。
- 全URIの解決・重複排除後、要求開始前に全対象の取得済み実ストア情報で復元可否を検査する。復元中・復元済み・即時取得可能等の不適格な対象が1件でも判明した場合、コマンド全体をエラーとし、復元要求は1件も送らない（2026-11-19確定）。付属の事前インデックス反映は残ってよい。
- 列挙・事前照会で復元状態が不明な対象が残る場合は、その対象だけ追加照会して復元可否を確定する。追加照会の失敗や、それでも可否を確定できない対象が1件でもある場合、コマンド全体をエラーとし、復元要求は1件も送らない。追加照会は要求操作に必要な事前検査であり、付属のインデックス保存失敗のwarningとは区別する。通常lsの不明値補完にはこの経路を使わない（2026-11-20確定）。
- 事前検査はその後の状態変化や復元APIの成功を保証しない。要求開始後は最初の要求操作の失敗で停止し、受付済み復元要求を取り消さない。付属のインデックス異常はwarningとして扱う。S3インデックスは途中失敗時も収束予算内で終了時1回の書戻しを試み、競合はその実行内で通知して終える。未送信状態を後続実行の前提として管理しない。途中失敗の具体的な表示は引き続き整理する。
- Phase 1 の対応ストアはS3のみ。B2・Wasabi等のadapter追加は別のスコープとする。

根拠: [RestoreObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_RestoreObject.html)、[S3 Batch Operations pricing](https://aws.amazon.com/s3/pricing/)。

## 更新操作の手順と失敗の扱い

1. `cp`・`rm`・`restore` では、操作対象として指定された範囲を実ストアから列挙・照会する。
2. 得られた情報のインデックス反映を試みる。失敗時はwarningとする。
3. 取得した実ストアの照会結果で判断できる実行可否を判定する。インデックスへ書き込めなくても、この情報を使って判定する。
4. 要求された実データ操作を実施する。
5. 成功した操作の結果のインデックス反映を試み、要求操作の成否で終了する。インデックス反映の失敗はwarningとする。

- 事前判定は実操作の成功を保証するものではない。実操作時のエラーも呼び出し元へ返す。
- 要求操作が失敗した時点で残りの処理を停止し、自動リトライしない。
- コマンド全体のatomicityは要求しない。失敗までに成功した実データ操作をロールバックしない。
- インデックス保存のためのトランザクションや回復処理を、実データ操作全体の原子性・永続的なイベント履歴の保証へ拡張しない。
- `sync` コアは、操作の失敗原因を詳細に呼び出し元へ返せること。CLIでの表示方法とは独立した要件とする。
- インデックス関係のエラーは発生時点・保存先にかかわらずwarningとして扱い、要求操作自体のエラーと区別する。要求されたコピー・削除・復元等の実行に必要な実ストア照会やキー解決の失敗は、インデックスの付属操作の失敗とは区別する。
- cpの事前確認・新規宛先・発行済み処理・キャンセル・成功分の反映は「Phase 1 cpの確定契約」に従う。rm・復元の実行順序と中断は次の確定契約に従い、対象なし等の残る契約はP2-01で決める。

### 削除・復元の実行と中断（2026-11-19確定）

- `rm`・`restore` の指定対象が実ストアに存在せず、要求処理を実行できない場合はエラー終了する。完全一致指定・再帰配下0件・全件ignoreのいずれも、上記「対象0件」の契約に従う（全件ignoreは2026-11-20追加確定）。
- `rm`・`restore` はオブジェクト単位で1件ずつ実行し、前の要求の成否を確認してから次へ進む。削除はキーの昇順、復元は前述のURI指定順・各URI内キー昇順とする。最初の要求操作の失敗で次の対象への要求を止める。
- `--parallel` 等による複数オブジェクトの並列実行は、ユーザが「あったらbetter、必須ではない」とした任意の改善候補とする。今回の完成条件と必須タスクには追加せず、現段階では実装しない。既存cpのmultipart内部の並列実行は別の契約として維持する。
- Ctrl+C・要求操作の失敗時は新規要求を止め、発行済み要求の終了確認と、確認できた結果の表示・インデックス反映を試みる。最初の中断・失敗からの収束予算は、cpと同じく付属処理を含め全体で最大50秒とし、段階ごとに予算を取り直さない。
- 通信切断・期限超過等で要求を発行した後の応答を確認できない場合は、成功・失敗・未変更を推測せず「成否不明」と通知し、正常終了にしない。自動再試行や確認目的の追加リモート照会は行わない。確認できた成功分は表示・インデックス反映を試みるが、実データ操作の成功を付属保存の成功に依存させない。
- 成功した削除や受付済み復元要求を取り消さず、成功済み操作をロールバックしない。強制終了・電源断後の結果保存までは保証しない。

### 未完了multipartの後始末

- アップロード失敗・Ctrl+Cによる中断時は、その操作が開始した未完了multipart uploadの中断・パート削除を試みる。他プロセスのアップロードを一括で中断する操作にはしない。
- 後始末も失敗した場合は、元の要求操作の失敗・中断に加えてwarningを通知する。後始末が成功しても要求操作の失敗・中断を正常終了には変えない。自動リトライは要求しない。
- 強制終了等で残った未完了分はS3 Lifecycleで回収する。Terraformで作成するバケット全体に、開始から1日後を削除対象とする `AbortIncompleteMultipartUpload` を含める。
- 日数はアップロード開始から数え、無通信になってからの時間ではない。転送中でも期限を超えて未完了なら中断対象になりうる。1日ちょうどでの削除完了は保証しない。
- 合意値は1日とする。日数パラメータの具体的なTerraform定義は設計段階で決める。1日未満への短縮は下記調査の不確実性を残し、0日や時間単位の削除を保証する要件にはしない。

調査結果（2026-11-15）:

- 未完了パートには保管料がかかり、Deep Archive向けでも転送途中のパートはStandard相当のステージング保管料となる。未完了分の削除には、保存クラスにかかわらず早期削除料金がない。再利用しない不要なパートを保持する費用上のメリットはない。
- Lifecycleの指定は整数の日数であり、時間単位の指定項目はない。CloudFormationの現行資料には `DaysAfterInitiation` の最小値0、旧REST資料には正の整数と記載されており、S3 APIでの0日の実際の受理・動作は未検証。「1日が最短」とは断言しない。
- `AbortMultipartUpload` と進行中のパート転送が競合すると、1回の中断で全パートが解放されない場合がある。パート要求の停止・収束と中断処理の順序は設計で決め、Lifecycleも残存分の回収に用いる。

根拠: [multipartの課金](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpuoverview.html)、[Lifecycleによる中断](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpu-abort-incomplete-mpu-lifecycle-config.html)、[中断API](https://docs.aws.amazon.com/AmazonS3/latest/API/API_AbortMultipartUpload.html)、[CloudFormationの値制約](https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-properties-s3-bucket-abortincompletemultipartupload.html)、[旧RESTの値制約](https://docs.aws.amazon.com/AmazonS3/latest/developerguide/v1-rel-RESTBucketPUTlifecycle.html)。

### 要求操作ごとのインデックス異常の扱い

| コマンド | 要求操作 | インデックスに関する異常の扱い |
| --- | --- | --- |
| `cp`・`rm`・`restore` | データのコピー・削除・復元要求 | warningとして通知し継続。要求操作の成否で正常終了・エラー終了を決める |
| `ls` | ローカルインデックスの問い合わせ | 問い合わせを完了できなければエラー終了。未作成時の空での初期化は既定の扱いに従う |
| `reconcile` | リモート状態を取得し、インデックスへ反映して結果件数を返す | 要求された取得・更新を完了できなければエラー終了 |
| GUIのディレクトリ配下の再照合 | 指定範囲のリモート状態を取得し、インデックスを更新して表示 | 要求された取得・更新を完了できなければ操作失敗として通知 |

- `reconcile` の列挙が途中で失敗した場合は、取得できた分のインデックス更新を残してエラー終了する。未取得範囲を削除済みと判定せず、その既存記録を残す。成功済み反映のロールバックや自動再試行を行わない。
- GUIの再照合も同じ部分失敗の契約に従い、取得できた分の反映と未取得範囲の既存記録を残して失敗を通知する。

## 同時実行と競合

- 参照同士、参照と更新、更新同士の複数CLI実行を想定する。
- 実データへのコマンド実行を直列化したり、実行中操作の状態を永続管理したりする仕組みは要求しない。
- 完了した操作の結果を、操作完了の順にインデックスへ反映する方針とする。コマンド全体の原子性は要求しない。
- コピー中に別プロセスがコピー元を削除する等の競合を、CLIが事前に防止・追跡する必要はない。
- SDKが操作エラーを返したら詳細な原因を呼び出し元へ返す。SDK上で成功した操作について追加の競合検知は行わない。
- インデックスへの読み書きを成立させる具体的なDB・ファイル操作の方式は設計で決める。操作全体の排他管理や実データのロールバックとは別に扱う。

## メモリと非同期実行

- データのサイズや対象ファイル数に比例して、使用メモリが増える実装にしない。
- ファイル転送・リモート一覧・ローカル走査・インデックス列挙・結果出力は逐次処理できる構造にする。
- ファイル全体、全対象一覧、全結果をメモリに保持することを前提にしない。
- Tokio による非同期処理を積極的に用い、長時間のブロッキング操作を非同期実行スレッド上で行わない。
- バッファ、キュー、同時実行数、DBキャッシュ等に上限を設ける。Phase 1の設計値と検証基準は [転送・検証計画](TRANSFER_VALIDATION.md) に記す。
- TLS・暗号・DB等の実装言語自体は制限せず、追加の実行時依存を不要にするという移植性要件に従って選ぶ。

## 認証

- 認証の選択・準備はCLIの外で行う。CLI自身に具体的なIAMロール名・専用プロファイル名・権限構成を持たせない。
- AWS SDKの標準認証解決を利用し、環境変数・共有AWS設定で渡した認証を使えること。
- 現状の `admin`・`dev` プロファイルは `default` を元に MFA 付きでロールを引き受ける設定。
- アプリ用の専用IAMロールを用意する。使用ロールの選択はBashラッパー等が外部から行う。
- MFAを伴う既存ユーザに代え、専用ロールへのAssumeRoleだけを許可した最小権限IAMユーザを作成し、固定アクセスキーを引受元の認証に使う方針とする。
- 専用IAMユーザの作成・権限定義はTerraformに含める。アクセスキーは操作者がAWS Webコンソールで発行する方針とし、TerraformやCLIでは発行・秘密値の管理をしない。
- ロールの権限は対象バケットでCLIが必要とする最小範囲とする。任意URIを扱えるCLIの機能と、与えられた認証情報の許可範囲を分離する。
- この要件定義作業では AWS 設定・IAM・リソースの変更は行わない。

### AWS認証の調査結果

- RustのAWS SDKは `AWS_PROFILE` で共有設定のプロファイルを選択できる。`role_arn` と `source_profile` によるAssumeRoleもサポートする。
- 標準チェーンではアクセスキーの環境変数が共有プロファイルより優先される。ラッパーで専用プロファイルを選ぶ際は、既存セッションのアクセスキー環境変数を子プロセスに持ち込まない案とする。
- この認証経路ではAWS CLIによるセッション取得コマンドをアプリの実行時依存にする必要はない。

根拠: [AWS SDK for Rust credential providers](https://docs.aws.amazon.com/sdk-for-rust/latest/dg/credproviders.html)、[Assume role credential provider](https://docs.aws.amazon.com/sdkref/latest/guide/feature-assume-role-credentials.html)。

- 大容量転送の早期検証に使えるよう、Phase 1に新規S3バケット、アプリ用IAMロール、AssumeRole用IAMユーザのTerraform定義を含める。

### 料金比較に基づくリージョン選定

## 到達点と段階

### Phase 1: 大容量転送を先に実用化する

- 約100GBの単一ファイルを扱えるCLIのcpを先に提供し、ローカル→S3・S3→ローカル・S3→S3の3方向を検証する。
- ストリーミング、Tokio、有界なバッファ・キュー、multipart、失敗・Ctrl+C時の後始末、実ストア照会に基づく実行判断を最初から含める。
- cpに必要な共通設定・ignore・ローカルインデックス反映・属性のbest effort保持を含める。インデックス異常は要求操作と分離する。
- 導入用のTerraform定義とCLI用Bashラッパーを含める。実装と大容量を想定した検証をこの段階へ置き、GUIや全CLI機能の完成待ちにしない。検証はDocker上のS3互換サーバーを使い、100GB実転送とAWSへの適用は完了条件に含めない。

### Phase 2: CLIと運用を完成させ、同時起動・移行を検証する

- cfg、一覧・詳細・JSON、再照合、S3上のインデックス同期、削除、複数URIの復元要求をそろえる。
- 同時起動、部分失敗、外部変更、設定・インデックスの移行、追加の実行時依存を必要としないCLI構成を検証する。
- 大量件数・約2TB規模を想定した列挙等の検証を行う。Phase 1で縮小サイズの転送と100GB相当の分割・制御経路を先行検証し、実際に転送した容量と区別する。

### Phase 3: GUIを最後に追加する

- Slintのカラム・詳細表示、ローカル再読込、再照合、設定値更新UI、GUI用ラッパーを提供する。
- GUIを含む現在のmacOS・ARM macOS・ARM Linuxへの移行、CLIと同じインデックスの共用を検証する。
- 各段階で必要な検証を行い、最後に完成範囲全体の受入条件を確認する。

### 今回の完成目標（合意済み）

- S3対応CLI・Terraform・Bashラッパーをそろえ、大容量転送・同時起動・端末移行まで検証できた状態を完成目標とする。
- 追加で、カラム表示による階層一覧を表示するSlintの独立GUIを含める。CLIと設定・インデックスを共用し、指定範囲の再照合と設定値更新UIを提供する。GUIも現在のMacと将来のARM macOS・ARM Linuxへの移行対応を完成条件に含める。
- B2等の追加ストアとGUIからのコピー・削除・復元等は将来の拡張候補とし、必要になった時点で別途要件化する。拡張できるコア分離は今回の要件に含める。

### 一覧専用GUIの要件

- Finderに倣ったカラム表示とし、最左列にバケット一覧、フォルダ選択で右隣の列に配下を表示する（2026-11-21、ツリーウィジェット案を置換）。インデックスに記録されたキーのprefixからディレクトリ相当の階層を構成し、空ディレクトリを新たに保存する要件にはしない。
- 各列の行は名前とファイル/フォルダの区別を中心にし、選択項目のサイズ・保存クラス・復元状態等は右の詳細欄へCLIと共通の基本10項目としてまとめる（2026-11-21確定）。本文・サムネイルは取得しない。未取得は不明とし、表示項目のための追加リモート照会を行わない。
- 一覧表示のコアを再利用し、DB技術・S3 SDK固有の型へGUIを依存させない。表示にはignore等の共通規則を適用する。
- Slintの独立アプリとし、CLIと同じ設定・インデックスを利用する。認証はshell-scriptsリポジトリのGUI用ラッパーから渡し、GUI本体へロールやプロファイルの具体名を固定しない。
- 起動・フォルダ選択・一覧表示・ローカル再読込ではS3を自動照会しない。初回でローカルインデックスが未作成でもこの方針を維持する。
- 操作者が指定したディレクトリ配下について、明示操作で `update-index` を実行できる。S3インデックスの確認・取得と、指定範囲の実ストア照会・インデックス反映はCLIと同じコアを利用し、指定範囲外を自動走査しない。
- 更新対象はカラム表示から選択し、トップレベルからの「再照合」も提供する。トップレベル更新の対象はインデックスに記録済みのバケットだけとし、それぞれの配下を照会する。対象バケット内で見つかった未記録キーも取り込む。AWSからバケット一覧を取得して対象を自動追加しない。
- 未登録ディレクトリのURIを直接入力する機能は不要とする。初回などバケットが未記録ならGUIのトップレベル更新に対象はなく、CLIで最初の対象を取り込んでからGUIでその記録を利用する。
- 表示のignore基準は開いた表示起点URIに固定し、展開・選択で変えない。再照合では更新対象のディレクトリを基準とする。トップレベル表示・更新では各バケットのルートを基準に同じパターンを適用し、照合する相対パスにバケット名を含めない。
- 設定値更新UIも今回の完成範囲に含め、CLIと同じ設定ファイル・値の検証契約を使う。設定画面を開くだけでファイルを作成したりS3へアクセスしたりせず、利用者の明示的な設定作成・保存で行う。キャンセルは未保存編集を破棄し、項目の既定値復帰は保存値を取り除く意味とする。保存は進行中操作を書き換えず次の操作から適用し、起動引数の上書きは維持する。
- 再照合の失敗は操作失敗として通知する。取得途中の失敗時には取得済み反映を残し、未取得範囲の既存記録を削除しない。通常閲覧中のインデックス異常も判明した詳細を通知し、自動再構築しない。
- GUIも現在のx86_64 macOSと、将来のARM macOS・ARM Linuxへの移行を対象にする。必要な設定・インデックスを移し、対象向けに再ビルドして利用を継続できること。GUIの具体的なウィンドウ環境・レンダラ・実行時依存の構成は設計段階で検討する。
- 再照合は単一選択とし、ディレクトリ/バケット配下は既定で再帰・深さ無制限、必要時は深さを指定できる（CLIの--recursiveのみと同じ）。ファイル選択ではその1件だけ更新し、再帰・深さは適用しない。複数選択の一括更新は追加しない。
- 表示済みの列の一括再読込は明示操作だけとし、URIで選択・開いている階層を保持、消えた対象は残る親階層へ戻す。フォルダ選択は、その選択時点のローカルqueryとして行う。画面状態は起動中だけで、再起動用の履歴を保存しない。共有設定も明示再読込で読み直し、インデックス保存先が変わったら新しいルートへ戻す。
- GUIからの再照合は同時に1つ。進捗・キャンセルを提供し、取得済み反映を残したまま最大50秒の収束予算で停止する。更新中のウィンドウ終了は確認ダイアログなしでキャンセルし、後始末後に終了する。自動再試行・次回実行への操作引継ぎはしない（2026-11-21確定）。
- 実データのコピー・削除・復元は今回CLIから実行する。将来はGUIの選択ファイルからローカルへコピーする操作等へ拡張する想定を持つ。コマンド・起動引数の形式と共通用語は設計段階でもユーザと確認する。

| IAM | API名とIAM action名は一致しない。HEADはGetObject、LISTはListBucket、コピーはコピー元GetObjectとコピー先PutObject、復元はRestoreObjectが基本。multipartの中断等にも別の必要権限がある。確定した呼び出しだけに必要な権限へ絞り、アプリ自身にロール知識を持たせない。[対応表](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-with-s3-policy-actions.html) |

### 調査では確定しない利用者向けの選択

- 複数URIの復元順序・全件事前検査と、全CLIの深さ指定条件は2026-11-19に確定。途中失敗の表示・書き戻し等は引き続きレビューする。
- rm・復元の逐次実行と最大50秒の中断収束予算は2026-11-19に確定。対象なし・出力・保存等の残る契約は引き続きレビューする。
- ローカルダウンロードの部分ファイルは一時ファイルへ書き、失敗時削除・既存宛先保護と確定した。
- 出力値・JSONの具体的な表記・終了コード、性能検証の具体値、一覧専用GUIの詳細と提供段階ごとの達成条件。

DB製品の選定、スナップショットの生成方式、SDK構成、具体的なIAM JSON等は、上記の利用者向け契約をもとに設計で決める。

## 合意済み事項の受入例

- 通常の再帰一覧ではインデックスに未記録の外部追加ファイルを表示せず、S3インデックス自体も含めS3 APIを発行しない。
- 指定prefixへ `reconcile URI --recursive` を実行すると、その範囲の外部変更を反映して件数を返す。続くlsで結果を参照でき、指定範囲外を再照合しない。
- 更新系操作では、以前のインデックスに未記録でも指定範囲の実ストア列挙で見つかったファイルを、実行可否の判定対象に含める。
- 逐次実行の例で、aが成功、bが失敗した場合、aの実データ更新は残り、cの処理とbの自動リトライは開始しない。bの詳細エラーをコアから返す。
- コピー自体が成功した後のS3インデックスPUTだけが失敗した場合、コピー結果を維持し、インデックス保存失敗をwarningとして通知する。
- 保存クラスの設定も実行時指定もないアップロードはstandardを使い、設定値があればその値、実行時指定があればそれを優先する。
- 復元保持期間を省略したコマンドは入力エラーにし、既定期間での復元要求を送らない。helpで期間の指定方法を確認できる。
- `7d` と `1w` はともに7日として扱い、`32h`・ゼロ・負の期間は入力エラーにする。
- 復元要求の受付後は復元完了を待たずに終了し、状態確認のためのポーリングを自動で繰り返さない。
- 有効なignoreに一致するファイルは、インデックスに記録されていても一覧に出ず、再帰コピー・削除・復元の処理対象にもならない。
- `--ignore ""` の実行では設定ファイルの除外を適用せず、次のオプションなしの実行では元の設定を使う。
- ignoreされていないシンボリックリンクの操作はエラーにする。除外済みのリンクの存在だけではエラーにしない。
- 空ディレクトリ用の保存オブジェクトを作らず、通常ファイルを自動圧縮・集約しない。
- 対応するOS・ファイルシステムでは元の属性の復元を試みる。作成日時等を復元できなくても、内容の取得が成功したコピーはwarning付きで正常終了する。
- 設定可能な項目はすべて実行時に置き換えられ、その指定が設定ファイル・組み込み既定値より優先する。明示指定必須の復元期間を設定から補完しない。
- ignoreの設定がなければ `.DS_Store` を暗黙に除外しない。CLIのカンマ区切り一覧は設定の一覧を置き換える。
- ignoreなしの再帰コピーでは `.DS_Store`、`.git/config`、隠しディレクトリ内の通常ファイルも対象になる。これらを除外するにはignoreを明示設定する。再帰一覧・再照合等でも隠し名による暗黙の除外を行わない。
- ignore対象を直接指定しても内容の読み書き・復元・削除を実施せず、warningでスキップする。
- リモートの `path/to` を指定しignoreに `skip/**` を設定した場合、`path/to/skip/file` は除外される。指定対象を `path` へ変えた場合は照合相対パスも変わり、以前と同じ除外になることは保証しない。
- CWDや操作対象の周囲に `.gitignore` が存在しても、除外判定に影響しない。
- 設定・インデックスを別の対応OS・アーキテクチャへ移した後、CLIをその対象向けに再ビルドして既存データを利用できる。追加のDB・TLS共有ライブラリやAWS CLIを実行時に導入する必要がない構成にする。
- 複数CLIの参照・更新を許し、コピー元の同時削除等でSDKが返した失敗は詳細エラーとして伝える。SDKが成功した操作を追加の競合検査で失敗にしない。
- ラッパーで指定したAWSプロファイルをSDKが利用し、CLIに具体的なロール名・プロファイル名を固定せずに実行できる。
- Terraformで新規バケット・ロール・AssumeRole専用ユーザを用意でき、バケットのバージョニングは無効である。アクセスキーはTerraformやCLIが発行せず、操作者がWebコンソールで発行する。
- ローカル→S3、S3→ローカルに加え、S3→S3のコピーが行える。
- 復元方式を設定・実行時に指定しなければBulkを使うが、復元期間は引き続き必ず実行時指定する。
- 設定ファイル未作成でも組み込み既定値を参照でき、通常コマンドは設定ファイルを作らない。設定可能な各項目をcfgから変更できる。
- index adapterを置き換える際、CLI・sync・インデックスの業務ロジックにSQLite・redb固有の変更を必要としない。
- 非再帰の `ls s3://bucket/foo` は、完全一致オブジェクト `foo` を表示し、`foo/a.txt` や `foobar/c.txt` は表示しない。
- 再帰コピーの `cp photos s3://bucket/backup/ --recursive` で `photos/a.jpg` は `backup/a.jpg` になる。コピー元の末尾 `/` の追加で `backup/photos/a.jpg` に変わらない。
- 非再帰の `cp photos/a.jpg s3://bucket/backup` はキー `backup` に保存し、コピー先の末尾に `/` があれば `backup/a.jpg` に保存する。
- `foo`・`foo/a.txt`・`foo/sub/b.txt`・`foobar/c.txt` がある場合、非再帰の `rm s3://bucket/foo` は `foo` だけを対象にする。再帰の `rm s3://bucket/foo --recursive` は `foo/` 配下の2件だけを対象とし、`foo` と `foobar/c.txt` を残す。`foo/` を指定しても再帰削除の範囲は変わらない。
- 深さ1と深さ2で直下・その1階層下を区別でき、指定なしでは再帰深さを制限しない。
- 1回の `restore` で再帰・非再帰・異なる深さのURIを混在指定できる。全体の復元保持期間は共通に適用し、あるURIの再帰指定を後続URIへ引き継がない。
- 復元対象のどこかに復元中・復元済み・Standardの対象があると事前照会で判明した場合、全体をエラー終了し、ほかの適格対象にも復元APIを送らない。要求開始後の状態変化やAPIエラーでは後続要求を止め、受付済みの要求は取り消さない。
- `ls`・`rm`・`restore` でも `--recursive-depth 1` だけの指定と深さ0は入力エラーになる。復元ではURIごとに `--recursive` の併用を検証する。
- 復元にprefix B、prefix Aの順でURIを指定した場合、B内のキー昇順、次にA内の未処理キー昇順で要求する。両URIに含まれるキーはB側で1回だけ処理する。
- `photos --recursive` と `photos/a.jpg` を同時に復元指定しても、全URIの解決・重複排除後に `photos/a.jpg` への要求は1回だけ送る。後半のURIの解決に失敗した場合、前半のURIへの復元要求も開始していない。
- S3インデックスが設定されていても、ローカルコピー未作成の通常 `ls` はローカルに空で初期化して空の結果を返し、S3へのGET・HEAD・LIST・PUTを発行しない。
- 空の初回lsと全件ignoreのcp・rm・復元は対象0件エラーとして `1`。JSONのlsは `[]` をstdoutへ出してerrorをstderrへ出す。設定ファイルで `logging.level = "warn"` としても、`--log-level debug` の実行ではdebugまで有効になり、再帰の個々のignore対象を確認できる。設定ファイル自体は実行時上書きで変更しない。
- インデックス破損を検出したら、判明した破損箇所・原因を表示する。lsの要求操作を完了できなければエラー終了し、コピー・削除・復元ではwarningとして要求操作を継続する。自動的なS3走査・再構築・空インデックスへの置き換えを行わない。
- 更新系操作でS3インデックスの取得やローカルの事前反映に失敗しても、必要な実ストア照会と実操作が成功すればwarning付きで正常終了する。インデックスを問い合わせできることを前提にしない。
- `reconcile` が2ページ目の取得で失敗した場合、1ページ目の取得済み更新を残してエラー終了する。2ページ目以降で取得できなかった既存記録は削除しない。
- multipartアップロードの失敗・Ctrl+C時は、その操作の未完了アップロードの中断を試みる。後始末の失敗もwarningで通知し、元の失敗・中断の結果を維持する。
- Terraformの定義にはバケット全体の未完了multipart uploadに対する開始1日後のLifecycle中断設定が含まれる。実際の削除完了時刻を1日ちょうどとは保証しない。
- JSON出力中にインデックス関連のwarningや転送進捗が発生しても、それらはstderrだけに出力され、stdoutの結果JSONへ文字列として混在しない。
- JSON配列に結果を2件出力した後で要求操作が失敗した場合、stdoutが利用可能なら2件の配列として閉じ、stderrにエラーを出して非ゼロ終了する。結果をメモリに全件保持してから出す方式を必須にしない。
- `rm` は実対象の列挙とignore適用を終えてからURI・件数・合計サイズを表示し、コマンド全体で1回確認する。`--auto-approve` がなければ、`yes` を受け取る前に削除を開始しない。
- `printf 'yes\n' | private-archive rm s3://bucket/key` は、パイプ内の文字列を承認として読まず、S3照会・削除前にエラー終了する。`--auto-approve` なら非端末入力でも承認読み取りを行わず実行できる。stdoutのリダイレクトだけを理由に拒否しない。
- 元の作成日時・UNIX権限等が未取得でも、ls詳細・JSONはそれらを不明として表示し、補完のためのHEAD等を発行しない。通常lsの表示やS3インデックスの取得だけで、最終照会日時を更新しない。
- CLIの通常一覧はURI昇順の1行1URI、詳細・JSONは基本10項目となる。prefix相当のサイズ等を埋めるための集計・追加APIは行わない。復元で事前検査時に状態不明な対象があれば、その対象だけ追加照会し、確定不能・照会失敗なら全対象への復元要求が0件のままエラーになる。
- ignore設定後も既存レコードは残るが一覧・操作から除外され、ignore解除で再び表示できる。除外中に新たな対象を取り込まず、未記録対象は解除後の再照合で取り込む。
- 一覧専用GUIで、インデックスに記録された `photos/a.jpg` と `photos/travel/b.jpg` を、photos・travelの階層を、フォルダ選択で右隣へ内容を表示するカラムとして閲覧できる。表示のための自動S3照会を行わない。
- GUIのローカル再読込ではS3 APIを発行しない。ディレクトリ配下の更新を明示実行した場合だけ、その範囲を実ストアから取得してインデックスを更新する。途中失敗では取得済み反映を残して失敗を通知する。
- shell-scripts側のGUI用ラッパーが認証プロファイル等を渡せ、GUI本体に具体的なロール名を固定せずに再照合できる。設定・インデックスをARM macOS・ARM Linuxへ移してGUIを再ビルドした後も利用できる。
- GUIはトップレベル・バケット・ファイル階層を区別して表示し、行にファイル名・サイズ・保存クラス・復元状態、選択時に基本10項目を表示する。
- GUIの設定値更新UIから共有設定ファイルの値を編集・保存でき、CLIでもその値を利用できる。設定操作自体でS3 APIやインデックス移行を自動実行しない。
- GUIトップレベルの再照合は記録済みの各バケットを対象とし、AWSから新たなバケットを発見しない。記録済みバケットがなければS3 APIを発行せず、最初の取り込みはCLIから行う。
- バケット内の最後のオブジェクト記録が削除されたら、そのバケットはlsのルート一覧とGUIのバケット一覧から消える。バケットだけを再発見用の管理対象として保持しない。
